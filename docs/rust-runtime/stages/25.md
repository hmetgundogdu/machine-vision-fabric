## What was built

- **Commands on the local endpoint** (`mvf_management::command`):
  - **The commands:** `stop`, `pause`, `resume`, `set-value`, `configure`, `replace`,
    `rollback`, `commit`.
  - **Validation:** each becomes the same update-plan step `mvf-rs run --updates` uses
    (`parse_update_plan`). The engine applies it at a cycle boundary through its `ControlHandle`.
    `stop` cancels the run cleanly at the next boundary. Replacement candidates resolve through
    the host's resolver, so contracts must stay inside the package.
  - **The reply is the engine's verdict,** read from the feed's own events:
    - `applied`, with the event;
    - `rejected`, with the reason;
    - `pending`, with `afterSeq`, when the deadline passed (default 5 s, at most 60 s);
    - `refused`, when nothing was sent.
  - **Idempotency:** the key is principal + `id` (the last 4096 are kept). A repeat is never
    re-sent; it gets the first reply with `"duplicate": true`.
  - **Audit:** an append-only JSON-lines log (mode 0600, synced) of every command, refused ones
    included, and of refused connections. The default is `<pipeline dir>/.mvf/audit.jsonl`.
  - **Shutdown** delivers the replies of commands in flight before the endpoint closes. The test
    for `stop` found that the process could exit first.
- **Sessions and roles:**
  - `observer` and `operator`; the owner is `local`/operator.
  - A client running as the owner may say `onBehalfOf: {principal, role, via}`. The role is
    capped at operator, and an unknown role is refused.
  - `hello` replies with the principal, the role and `features: ["commands"]` when commands are
    allowed.
- **`mvf-remote`** (new crate and binary). Its rustls/ring TLS stack stays out of the runtime:
  - **`serve`** is the relay. It listens only on the `--listen` address it is given, speaks TLS
    1.3 with client certificates, and checks each connection against the access list
    (fingerprint → name and role, plus revocations, re-read for every connection). It connects
    to the local endpoint `onBehalfOf` the principal, and refuses an observer's command itself.
    - Limits: 8 clients, a 5 s handshake, a 5 min idle timeout, a 5 s write timeout, 64 KiB
      requests.
    - It keeps its own audit log of admitted and refused connections and forbidden requests.
    - Without `--endpoint` it finds the runtime again for every connection, so it follows a
      restarted runtime.
  - **`pki init|issue|revoke`:** a private CA (ECDSA P-256), the relay's certificate, per-client
    certificates and the access list. Keys are 0600, and an existing CA is never overwritten.
  - **`status`, `watch` and `command`:** the remote client. `watch` reconnects from the last
    sequence it saw.
- **CLI:** `mvf-rs run --manage [--audit FILE]` attaches the run's controls, and `mvf-rs manage
  command NAME --id … [--node --value --field --module --builtin --contract --config --for-ms
  --deadline-ms]` sends commands. Exit codes: 0 applied, 3 pending, 1 otherwise.
- **The Python client** (`clients/mvf-manage-py`) gains `command` and `--remote host:port --ca
  --cert --key` over the standard library's `ssl`.

### Commands

```text
$ mvf-rs run --manage pipeline.yaml
$ mvf-rs manage command set-value --node thr --value 41 --id ops-1
$ mvf-remote pki init --dir pki --host panel-07 --host 10.0.0.7
$ mvf-remote pki issue --dir pki --name alice --role operator
$ mvf-remote serve --pki pki --listen 10.0.0.7:7443
$ mvf-remote command --connect panel-07:7443 --ca ca.pem --cert alice.pem --key alice.key stop --id ops-2
$ python3 clients/mvf-manage-py/mvf_manage.py --remote panel-07:7443 --ca ca.pem --cert alice.pem --key alice.key status
$ cargo test -p mvf-management -p mvf-remote
$ MVF_REMOTE_BENCH=1 cargo test --release -p mvf-remote --test remote bench -- --nocapture
```

## Limits

- **No artifact upload or previews:** part 3. `replace` takes candidates already on the box.
- **The CA key sits in the PKI directory** so `pki issue` can sign. In production keep it
  offline and issue short-lived certificates. There is no CRL or OCSP: revocation is the access
  list, effective on the next connection. An open connection keeps its session until it closes
  (idle timeout 5 min).
- **The relay runs as the runtime's user** and is trusted to say `onBehalfOf` honestly, like any
  same-user process (ADR-0007). Its own checks come first, and the runtime caps the role.
- **TLS 1.3 only.** A client stack without it, such as macOS's system Python on LibreSSL 2.8.3,
  cannot connect.
- **No interlocks beyond the engine's own.** MVF never bypasses node validation, but a physical
  stop or interlock on the machine is the PLC's job, not management's.
- **No measurements on industrial edge hardware.**
