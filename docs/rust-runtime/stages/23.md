runner, whatever the framing. This stage removes the thread hop on Windows as part 1 did on Unix.

## What was built

- **Windows direct receive (`crates/mvf-worker/src/process.rs`, module `direct`).**
  - Anonymous pipes can be neither polled nor read with a timeout. When v2 is offered, the host
    therefore makes the child's stdout the client end of a named pipe:
    - one instance (`FILE_FLAG_FIRST_PIPE_INSTANCE`), local clients only, with a unique
      per-launch name;
    - the host connects the client itself before the child exists, and `ConnectNamedPipe` must
      then report `ERROR_PIPE_CONNECTED`. A process that took the instance first makes the spawn
      fail; it cannot receive the channel.
  - **Reads:** the host reads the server end on the calling thread with overlapped `ReadFile` and
    a bounded `WaitForSingleObject` on its event, the counterpart of `poll`.
    - At most one read is outstanding, and a wait that times out leaves it in place for the next
      call.
    - Its buffer and `OVERLAPPED` live on the heap. Dropping the reader cancels the read
      (`CancelIoEx`) and waits for it before freeing them.
    - `ERROR_BROKEN_PIPE` is the end of the stream.
  - **v1 fallback:** a child that answers in v1 is detected by its first byte as before. Its
    lines are then read on a thread through a blocking `Read` over the same pipe.
  - **For the child it is an ordinary pipe handle.** No SDK changed, and SDK-side channel
    protection (stage 22) works as before.
- **One reader for both OSes.** The frame buffer, protocol detection and bounded `next(wait)` are
  shared. Only `fill` (wait, then read what is there) differs between Unix (`poll` + non-blocking
  `read`) and Windows (overlapped I/O).
- **Rollback switch.** `MVF_WORKER_RECEIVE=thread`, or `mvf_worker::process::set_receive_path`,
  keeps the reader thread for v2 on every OS. The thread path used to exist only on Windows; it
  now also gives same-run comparisons.
- **Tests.**
  - `crates/mvf-ipc/tests/receive.rs` runs the same cases on both receive paths: a healthy v2 run,
    a child answering a v2 offer in v1 (new fixture fault `v1-only`), a hung request and a
    half-written frame (both bounded by the 1.5 s deadline), a crash inside a frame (exit code 3),
    garbage on the channel (`Protocol`) and a stray print.
  - On Windows, every existing worker suite now runs over the named pipe, including fault
    injection, hardening, recovery, replacement, display, storage and the SDK suites.
- **Benchmark.** `engine_bench.rs` adds a `2t` row: v2 on the reader thread, next to `2`, v2
  direct.
- **Fixture.** `mvf-ipc-echo` now also needs `MVF_SESSION` to take a v2 offer, like the SDKs.

- **The direct path removes the Windows floor that stage 22 found.** In the same run it cuts the
  cycle time by 24–40 % against the reader thread, for every node.
- **v1 → v2 direct on Windows is now −43 % to −59 %** for Rust, C++ and .NET, and −26 % for Python.
  Python also logs a line every frame. Stage 22, on reader threads, had measured −4 % to −34 %.
- **Windows is now on a par with the other runners.** v2-direct cycle times are 23.5–25.6 µs for
  Rust, C++ and .NET, against 22.2–29.4 µs on Ubuntu and macOS.
- This run's Windows runner was faster than stage 22's (v1 Rust 45.3 vs 73.1 µs). Shared runners
  vary, which is why comparisons stay within a run.

## Limits

- **Windows evidence comes from GitHub's `windows-latest` runner only** (image `windows-2025`), a
  shared VM, not a panel PC. No Windows machine was available here.
- **The named pipe's security is the default descriptor.** It grants write access, which a
  client of this inbound pipe needs, only to the creator, LocalSystem and administrators; the
  instance is taken before the child starts. No custom DACL is set.
- **One outstanding read per child, one request in flight**, as before.
- **The child's stdin stays an anonymous pipe**, written synchronously. A request is at most a few
  hundred bytes and only one is in flight, so a write does not fill the pipe buffer. A child that
  stopped reading would block that write, as on Unix; the deadline does not bound it.
