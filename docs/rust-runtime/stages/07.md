# Stage 07 — OCI image import, verified content store and Docker interoperability (#17)

**Status: PASS** (hermetic tests on macOS locally and in CI; Docker interoperability verified
locally with Docker 28.5.1)

## What was built (`rust/crates/mvf-oci`, `mvf-rs image …`)

- **Content store** (`blobs/sha256/<hex>`, `images/<sha256(name)>.json`, `tmp/`): every blob is
  streamed into `tmp/`, hashed while written, and renamed into place only if digest **and** size
  match; identical content is stored once; `verify` re-hashes; `rm` + `gc` remove records and
  unreferenced blobs and stale temporaries.
- **Import without a daemon or network**: OCI image layout (directory or tar, optionally gzipped),
  Docker 25+ `docker save` archives (OCI layout + `manifest.json`), and legacy `docker save`
  archives (`manifest.json`, `<digest>.json`, `<id>/layer.tar`, symlinked duplicate layers).
  Nested indexes are walked to the requested platform (`os/arch[/variant]`, default
  `linux/<host arch>`); attestation manifests are skipped. Legacy archives are converted to an OCI
  manifest and every layer is checked against the config's `diff_ids`.
- **Fail-closed checks**: digest and size mismatches, traversal or absolute archive entry names,
  non-sha256 digests, unknown `imageLayoutVersion`, `zstd` layers (recognised, unsupported),
  unknown layer media types, nested index depth, layer count, JSON and blob size limits.
- **Safe unpack** to a rootfs: entry paths resolved inside the rootfs with securejoin semantics
  (symlinked parents followed but clamped to the root — needed for real images such as Debian's
  `bin -> usr/bin`), the final component never written through, `..`/absolute entries rejected,
  hard links confined to regular files inside the rootfs, OCI whiteouts and opaque directories,
  device nodes/FIFOs skipped and counted, setuid/setgid/sticky dropped, ownership not preserved
  (rootless), per-layer `diff_id` verification, size/entry/path limits, destination removed on
  any error.
- **Export** as an OCI layout tar or a Docker archive, blobs copied byte-for-byte and re-verified.
- **Builder**: deterministic layers (zero mtimes) and `append_layer`, enough to package an MVF node
  as an OCI-profile image without a Dockerfile engine (used in #18).

### Metadata convention

The MVF node contract travels **inside** the image filesystem (e.g. `/mvf/node.yaml`), and the
image config carries the label `dev.mvf.node.contract=<path>`. Nothing about the image format is
MVF-specific, so the label and file round-trip through any OCI/Docker tooling (verified by
`appended_layer_builds_a_derived_image` and by the Docker round trip below).

### Docker archive vs OCI layout

| | OCI image layout | Docker archive |
|---|---|---|
| Marker | `oci-layout` + `index.json` | `manifest.json` (+ `oci-layout`/`index.json` since Docker 25) |
| Blob paths | `blobs/sha256/<hex>` | Docker 25+: same; legacy: `<id>/layer.tar`, `<digest>.json` |
| Layers | as stored (gzip or tar) | Docker 25+: as stored; legacy: uncompressed tars |
| MVF import | `source: oci-layout` | `source: docker-archive` / `docker-archive-legacy` (converted, diff_ids checked) |
| MVF export | `--format oci` | `--format docker` (OCI layout + `manifest.json`) |

## Limitations

- No registry client (pull/push): images arrive as archives or layouts; `docker`/`skopeo`/`crane`
  can be used as optional preparation tooling.
- `zstd` layers, non-sha256 digests and foreign/non-distributable layer semantics are rejected.
- File ownership and extended attributes are not preserved (rootless unpack); device nodes are
  skipped.
- On macOS a case-insensitive filesystem can merge paths that differ only in case; real Linux
  rootfs should be unpacked on Linux (the #18 backend only runs there).
