## What was built

- **Engine.** `Observer::events` delivers replacement, recovery and live-edit events as they
  happen, at cycle boundaries and at the end of the run. Before, they only reached the run
  report. It defaults to a no-op, so existing observers are unchanged.
- **`mvf-management`** (new crate):
  - **`Feed`:** one sequenced stream of entries in a bounded ring (4096), plus the current
    state for snapshots. The entries are node deltas, engine events, logs, `dropped` counts and
    status.
  - **`Tap`:** the engine-side observer. It keeps per-node counters and a log-scale latency
    histogram (±4.5 %, 2 KiB per node) on the engine thread and publishes them every 100 ms
    with a non-blocking lock attempt.
  - **`Server`:** one accept thread and one thread per client; a client handler that panics is
    contained. Limits:
    - 8 clients;
    - requests of at most 64 KiB;
    - a 2 s write timeout on Unix;
    - heartbeats every second.

    On shutdown it waits up to 1 s for clients to receive the final status.
  - **Local endpoint authenticated by the OS:**
    - **Unix:** a private runtime directory (0700, must be owned by the user), a 0600 socket,
      and a peer-uid check on every connection. When the directory's path is too long for a
      socket address (about 104 bytes), the socket goes in `/tmp/mvf-<uid>`, checked the same
      way.
    - **Windows:** a named pipe with a DACL for the current user and LocalSystem, remote
      clients rejected, and an exclusive first instance.
  - **Discovery:** a registry file per runtime. All of it is removed when the run ends.
  - **`Client`:** `hello`, snapshot, and a subscription that resumes from a sequence.
- **API v1** ([`protocol/management-v1.md`](../../protocol/management-v1.md)), read-only:
  - JSON lines, versioned by `hello`;
  - a snapshot, then a strictly sequenced stream;
  - explicit `gap` followed by a fresh snapshot;
  - stable error codes.

  The topology never includes config values.
- **CLI:**
  - `mvf-rs run --manage` opens the endpoint for the run;
  - `mvf-rs manage list | status | watch`. `watch` reconnects, continues from the last sequence
    it saw, and resynchronises after a gap.
- **An independent client:** `clients/mvf-manage-py/mvf_manage.py`, Python standard library only
  (Unix socket or Windows pipe), with `list`, `status` and `watch`.

- **About 0.06 µs per cycle for four node events,** roughly 15 ns each, all on the engine
  thread. CPU per cycle equals wall time per cycle in every row.

  milliseconds.
- **Memory:** the ring holds at most 4096 lines, and each node's histogram is 2 KiB.

## Limits

- **Observation only.** No commands, no remote endpoint, no previews and no artifact transfer:
  parts 2 and 3.
- **The local owner is fully trusted.** Same-user processes, root and administrators are
  outside the threat model (ADR-0007).
- **Logs are forwarded as modules write them,** within the budget. A module that logs a secret
  exposes it to the owner's management clients.
- **On Windows a stuck client holds its own thread until it disconnects.** Synchronous pipe
  writes cannot time out. The engine and other clients are unaffected.
- **Percentiles are histogram estimates** (±4.5 %). `window` rates cover the last publication
  interval only.
- **No measurements on industrial edge hardware.**
