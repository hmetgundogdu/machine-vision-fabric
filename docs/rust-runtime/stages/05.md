# Stage 05 — Generation-aware live node replacement and rollback (#15)

**Status: PASS** (macOS arm64 locally; Linux/Windows in CI)

## What was built (`mvf-engine::replace`)

- **Local update API**: `Engine::control()` returns a cloneable, thread-safe `ControlHandle`
  (`replace`, `rollback`, `commit`). Commands are applied only at **cycle boundaries** by the single
  scheduling authority. CLI: `mvf-rs run … --updates plan.yaml` with a strict `kind: UpdatePlan`
  (same YAML loader, unknown fields rejected).
- **Validation before staging** (each with a stable code): unknown node (`replace.unknown-node`),
  source node (`replace.source-unsupported`), active contract `replacement: unsupported`
  (`replace.not-replaceable`), stateless/stateful mismatch (`replace.mode-mismatch`), state schema
  not importable (`replace.state-incompatible`), connected port missing or retyped / new required
  input (`replace.port-incompatible`), backend negotiation (`replace.negotiation`), one replacement
  at a time per node (`replace.in-progress`).
- **Preparation** on a background thread (instantiate + readiness within the candidate's budget)
  while the active generation keeps serving cycles. Failure → `replace.readiness-failed`, v1 stays.
  Ending the run mid-preparation cancels it, reaps a worker candidate and records
  `replace.aborted`.
- **Cut-over** at the first boundary after readiness: drain the active generation (nothing is in
  flight between serial cycles), export/import state for stateful nodes
  (`replace.state-migration-failed` keeps v1), switch routing to the new **generation** atomically.
  Generations are monotonic per node; the observer and `ExecContext` carry the generation that ran
  each cycle (fencing is structural: outputs exist only inside the cycle that produced them).
- **Probation + rollback**: the previous generation stays warm for `probationCycles`. A candidate
  failure during probation rolls back (`replace.candidate-failed`) and **re-executes the same cycle
  with the same inputs on the restored generation**, so the cycle is neither lost nor duplicated.
  After probation the previous generation is stopped (`committed`). Resource overlap is bounded:
  at most two generations of a node exist at once, for at most `probationCycles` cycles.
- **Stateful contract**: `lifecycle.state.{schemaVersion, migratesFrom}`; `counter` builtin with
  schema 1 (u64) → schema 2 (JSON) migration as the supported stateful fixture.
- Builtins keep payloads in the memory domain they arrived in (`invert` writes arena outputs for
  arena inputs), so replacements do not introduce copies.

## Timing is reported in two parts

`Promoted` events carry `preparationMs` (instantiate + readiness, overlapping with live cycles) and
`cutoverUs` (time the boundary is held for drain + state migration + switch). Example run
(`rust/examples/live-update`, 5 ms/cycle, macOS arm64):

```text
requested   cycle 20  gen 1 -> 2
promoted    cycle 29  gen 1 -> 2   prep=56.4 ms (Python worker spawn + hello, v1 served cycles 20–28)   cutover=11 µs
committed   cycle 39  gen 1 -> 2
requested   cycle 50  gen 2 -> 3
promoted    cycle 51  gen 2 -> 3   prep=0.17 ms   cutover=23 µs
rolled-back cycle 70  gen 3 -> 2   [replace.candidate-failed]   cutover=5 µs
frames 120/120, cycle ids 1..120 exactly once; data plane copiesIn=0 copiesOut=0 inUse=0
```

These are single-run observations on one machine, not benchmarks. **No claim of universal zero
downtime**: the boundary is held for the cut-over (µs here), a node whose readiness or state
migration is slow is still prepared off the critical path but its state export/import runs on it,
exclusive devices may need the old generation released before the new one can open them (not
modelled yet), and physical side effects of a failed candidate (e.g. a PLC write before failing)
cannot be rolled back.

## Limitations

- Sources cannot be replaced yet (exhaustion/sequence semantics need a design).
- Stateful replacement is implemented for in-process nodes; the worker backend declares only
  `stateless` (protocol v1 `checkpoint`/`restore` exist but are not wired for migration).
- Shadow evaluation (run v2 beside v1 without side effects) is not implemented (#20 scope).
- Rollback replays the failed cycle; it does not undo side effects the candidate already caused.
