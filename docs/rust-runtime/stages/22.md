**Correction to part 1.** Stage 21 said "the C++ and .NET SDKs speak v1". There was no .NET
*worker* SDK: `src/sdk/dotnet/Mvf.Sdk` builds in-process modules for the .NET engine and speaks no
worker protocol. Part 2 adds one.

## What was built

- **C++ SDK (`src/sdk/cpp`).** v2 when offered, v1 otherwise, with the same author API.
  - **Channel protection.** Private duplicates of fd 0 and fd 1, then fd 1 → stderr and
    fd 0 → null.
    - Windows: binary mode, non-inheritable handles, and `SetStdHandle` for code that writes
      through Win32 handles.
    - Unix: close-on-exec, and stdout line-buffered (it now feeds the logs).
  - **Hot path.** A buffered reader: one `read` per request and one `write` per reply. A
    processor's result is 24 bytes with no JSON. The frame-metadata JSON is reused and
    rewritten only where it changed.
  - **Logs** are JSON lines on stderr. `ping` is answered with `pong`.
  - **New example `mvf_mean_analyzer`:** classification + JSON value, a checkpointed frame
    count, and a deliberate `printf` to stdout on its first frame.
- **.NET worker SDK (`src/sdk/dotnet/Mvf.Worker`, new).**
  - `WorkerModule.RunClassifier`, `RunProcessor` and `RunAnalyzer`, with
    `ModuleHooks { OnStart, OnCheckpoint, OnRestore }` and `Log`.
  - v1 and v2 transports.
  - The arena is mapped once, with bounds checks on every slot. There is no per-frame
    allocation for metadata, and nothing beyond the base class library.
  - **Channel protection:** for managed code via `Console.SetOut`; for native code via
    `dup2` (libc found through the main program's global scope), or on Windows via
    `SetStdHandle` plus the C runtime's `_dup2`.
  - **Examples** (twins of the C++ ones): `InvertTransformer` and `MeanAnalyzer`. The analyzer
    writes to stdout from both managed and native code.
- **Negotiation hardening** (host and all three SDKs; [spec](../../protocol/worker-v2.md)).
  - A launch that offers only v1 now says `MVF_PROTOCOL=1`. Before, it said nothing, and the
    child inherited whatever the host's environment had.
  - An SDK takes v2 only with `MVF_SESSION` set as well. A stray `MVF_PROTOCOL=2` in a user's
    environment could otherwise switch a module running under the .NET engine, which never
    offers v2.
- **Tests:** `crates/mvf-worker/tests/sdks.rs` (7), see below.
- **Benchmark:** `crates/mvf-ipc/tests/engine_bench.rs`, the through-the-engine comparison moved
  out of the Unix-only `bench.rs`.
  - It is now portable, so CI measures Windows too.
  - It covers every SDK.
  - It adds the child's CPU per frame: a 50,000-frame run minus a 1-frame run, so process
    start-up is not counted.
- **CI:** the Rust job sets up .NET, publishes both examples, sets `MVF_REQUIRE_DOTNET=1` next to
  `MVF_REQUIRE_CPP=1`, and runs the benchmark on all three OSes. .NET is a test fixture there,
  not an engine dependency.

### Through the engine (`engine_bench.rs`, 50,000 8×8 frames after a 1-frame warm-up run)

µs per frame (node cycle time), max µs, and the child's CPU µs per frame. v1 → v2.

**macOS, M-series** (two runs; ranges):

| Node | µs/frame | max µs | child CPU µs/frame | frames/s (v2) |
|---|---|---|---|---|
| Rust analyzer (fixture) | 10.9 → 7.3 | 56–442 | 4.1–4.2 → 3.0–3.2 | 107k |
| Python transformer | 25.7–26.2 → 20.0–20.2 | 101–310 | 20.0–20.2 → 15.8–16.4 | 45k |
| **C++ transformer** | **14.7–15.2 → 5.2–5.3** | 80–232 | **9.2–9.5 → 2.1** | 138–139k |
| **.NET transformer** | **15.0–15.2 → 5.4** | 5,410–7,686 | **9.8–10.2 → 2.8–2.9** | 135–137k |

**Linux, aarch64 VM, 10 vCPUs** (`BENCH=1 rust/scripts/worker-sdks-linux.sh`), unpinned and pinned
with `taskset`:

| Node | unpinned µs/frame (CPU) | 1 CPU µs/frame (CPU) | 2 CPUs µs/frame (CPU) |
|---|---|---|---|
| Rust analyzer | 39.7 → 22.8 (7.6 → 5.9) | 6.5 → 4.1 (2.4 → 1.6) | 26.6 → 23.3 (6.7 → 6.0) |
| Python transformer | 47.8 → 14.3 (19.7 → 11.6) | 27.8 → 23.7 (10.9 → 8.9) | 52.6 → 44.0 (18.4 → 16.2) |
| **C++ transformer** | **39.0 → 21.6 (11.0 → 5.6)** | **10.3 → 3.7 (5.9 → 1.4)** | 40.8 → 21.7 (11.1 → 5.7) |
| **.NET transformer** | **36.2 → 3.4 (14.9 → 1.8)** | **14.5 → 3.4 (9.0 → 1.6)** | 34.8 → 3.3 (13.8 → 2.0) |

How to read these:

- **v2 cuts each SDK's child CPU per frame by 3–8×.** The cut is largest in C++, where
  nlohmann/json made v1 expensive. Latency falls 1.8–2.9× for C++ and 2.8–10× for .NET.
- **Unpinned VM numbers are dominated by cross-CPU wakeups.** Each side must wake the other on
  another vCPU, through an IPI and a VM exit. The cost depends on where the scheduler places the
  child. Pinned to one CPU, C++ falls to 3.7 µs and the Rust fixture to 4.1 µs, which shows the
  SDKs' own cost.
  - The .NET child avoided that wakeup cost even unpinned. Its CPU per frame (1.8 µs) shows it
    is not busy-polling. Why the scheduler places it better was not investigated.
  - Compare children within one column, not across hosts.
- **.NET has millisecond outliers.** Max cycle times of 5–9 ms come from the runtime's JIT
  tiering and GC. Means are unaffected. A node with a hard per-cycle deadline should account for
  them (ReadyToRun, tiering settings); they were not tuned here.
- **Python logs a line every frame** (`py.invert-transformer`). Its numbers include that, and on
  one CPU the log-delivery thread competes for it.
- **Readiness:** C++ 1–6 ms, .NET 33–64 ms, Python 15–64 ms, unchanged by the protocol.

The raw round-trip benchmark (`bench.rs`, Rust and Python children, stage 21) is unchanged.

## Limits

- **Windows evidence comes from CI only.** No Windows machine was available here, and the C++ SDK's
  Windows branch has been compiled only by CI's MSVC.
- **.NET on Apple silicon:** the protocol descriptors stay inheritable by processes the module
  itself starts. `fcntl` is variadic, and that ABI passes variadic arguments on the stack.
- **C++ and .NET support neither live `configure` nor the `source` capability.** Python supports
  both. This is a parity gap that predates v2.
- **.NET cycle-time outliers** of several milliseconds, see above.
- **The .NET engine's host stays v1-only** by design (the shipping engine is unchanged), so v1
  cannot be retired yet.
- **No measurements on industrial edge hardware.**
